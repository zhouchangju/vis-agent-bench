# 软件研发时间分配与 AI Coding 效能：外部研究证据审查

> 用途：为“可视化 AI 人效评估”领导汇报提供可引用的外部证据，并明确证据边界。
>
> 审查对象：用户提供的两份深度研究报告；研究截止日期为 2026-07-19。

## 审查结论

两份材料不能等权合并：

- **报告一可作为主要底稿**：优先引用论文、官方研究和有公开方法的实验，能区分受控任务、真实项目、主观调查与组织层观察，措辞总体克制。
- **报告二只保留分析框架**：它提出了“代码生成不等于交付”“要考虑验证税、返工和组织系统”等正确问题，但部分数字存在来源等级虚高、年份或样本混用、概念偷换和过度外推，不宜直接进入领导材料。

领导汇报应采用的总口径是：

> 外部研究没有给出一个适用于所有公司的“编码时间占比”或“AI 提效比例”。现有高质量证据共同说明：AI 的效果高度依赖任务边界、代码库成熟度、工程 Harness 和组织环境；简单、边界清晰的任务可能显著提速，复杂真实项目可能收益有限，甚至出现负收益。

## 可保留的核心证据

| 研究 | 研究对象与指标 | 可安全引用的结果 | 必须同时说明的边界 |
| --- | --- | --- | --- |
| Microsoft，*Today Was a Good Day* | 5,928 份可用开发者问卷；按一天活动分配时间 | “Coding”平均约占 15%（84 分钟）；会议约 15%，邮件约 10% | Coding 定义包含阅读/编写代码和测试，并非“纯敲代码”；单公司、自报数据 |
| Microsoft，*Time Warp* | 484 名开发者的实际/理想工作时间调查 | 实际工作周中编码约 11%，调试约 9%，架构设计约 6%，PR/Review 约 5% | 样本响应率低，仍是单公司自报；不能外推成全行业固定比例 |
| GitHub Copilot 受控实验 | 完成一个边界清晰的 JavaScript HTTP Server 任务 | 使用 Copilot 的处理组完成速度快 55.8% | 小型、受控、一次性任务；不能代表复杂生产项目 |
| Google 企业内随机实验 | 96 名全职工程师，真实开发任务的完成时间 | 校正后的最佳估计约节省 21% 任务时间 | 样本小、置信区间较宽；作者明确提醒不可直接外推到团队、生态和其他工具 |
| METR 真实仓库随机实验 | 有经验的开源维护者，在熟悉的成熟仓库解决真实 Issue | 使用 2025 年初 AI 工具后平均慢 19% | 是特定人群、仓库和当时工具快照；不能外推成“AI 一定降低效率” |
| DORA 2024 GenAI 报告 | 组织层调查与统计关联 | AI 采用增加与交付吞吐下降、稳定性下降相关 | 观察性关联，不是因果；不能写成“AI 导致下降” |
| DORA 2025 | 近 5,000 名技术从业者 | AI 使用与吞吐、产品表现呈正相关，但与稳定性仍呈负相关；核心判断是 AI 会放大现有系统的强弱 | 是组织层关联，不给单个模型或单个 Case 的确定提速值 |
| DORA 2026 定性研究 | 1,110 名 Google 开发者 | 发现“verification tax”：写代码节省的时间会部分转移到审查、验证和 Prompt；原型到生产仍存在鸿沟 | 定性研究适合解释机制，不应用作精确 ROI 数字 |

## 对“开发人员真正编码时间”的严谨回答

不能说“行业公认开发者只有 10%–20% 时间在编码”，更不能把它说成“纯粹敲键盘的时间”。

更安全的表述是：

> 两项 Microsoft 开发者研究中，研究定义下的编码活动处于低双位数区间（约 11%–15%）；但定义、样本和统计方法不同，且编码活动通常包含阅读代码、编写代码或测试。它们支持“研发工作远不只有编码”，不支持把某个比例直接当作我们团队的事实。

如果把 Microsoft 2019 表中的编码、Bug 修复、测试和代码 Review 全部称为“编码相关活动”，合计约
42%。这也说明“直接编码”“编码相关工程活动”“端到端交付时间”是三个不同口径，报告中必须分开。

## 对 AI Coding 效果的正确解释

现有研究不是彼此矛盾，而是在测不同任务：

```text
边界清晰、上下文较少、一次性交付
  → AI 更容易显著提速

成熟代码库、隐含约束多、质量要求高
  → 上下文理解、验证、返工和维护成本上升

组织具备测试、版本控制、平台和快速反馈
  → 更有机会把局部代码速度转化为交付速度
```

因此不能求一个“AI 平均能提效多少”的孤立数字。对可视化团队，更重要的是按工作类型分层测量：

1. 自由 Demo / POC；
2. 标准化组件和重复性需求；
3. 复杂真实产品需求；
4. 跨部门依赖和业务决策。

## 第二份报告中需要降级或删除的内容

| 原说法类型 | 处理 | 原因 |
| --- | --- | --- |
| “开发者每天只有 52–78 分钟编码” | 不作为核心证据 | 主要来自商业报告或自选择样本，口径和方法透明度不足 |
| 将 *Time Warp* 写成约 25% 编码 | 更正 | 原始研究的实际编码占比约 11%；25%可能混入其他活动或二次解读 |
| 把 DORA 的 1.5%/7.2% 写成 2025 结论 | 更正 | 该组数字来自 2024 GenAI 报告；2025 的总体方向已发生变化 |
| 把 GitClear、Faros、Sonar 等厂商分析定为 A 级证据 | 降为方向性线索 | 多为观察性或厂商研究，指标不能直接等价于业务交付质量 |
| “端到端纯编码低于 5%”“技术债增加 3 倍”等 | 删除，除非补充原始方法 | 当前材料无法支持如此确定、普遍的结论 |
| “无可辩驳”“必将”“毁灭性”等措辞 | 删除 | 超过证据能力，不适合管理决策报告 |
| Kimi K3 的上下文、审美或全面领先结论 | 仅写成待测假设 | 尚无与团队当前工作流同条件、同 Case 的独立实证 |

## Amdahl 推导如何使用

Amdahl 公式只能解释“局部环节变快对整体的理论影响”，不是实际 ROI 预测：

`端到端加速比 = 1 / ((1 - 局部工作占比) + 局部工作占比 / 局部加速倍数)`

以 Microsoft 2019 研究中的 15% “Coding”口径作纯数学示例：

| Coding 环节加速 | 理论端到端加速 |
| --- | --- |
| 2 倍 | 约 1.08 倍 |
| 5 倍 | 约 1.14 倍 |
| Coding 时间趋近于 0 | 约 1.18 倍 |

它不能证明我们团队的上限就是 18%，因为：

- 我们尚未测量本团队各活动的时间占比；
- AI 也可能作用于需求整理、测试、Review 和文档，而不仅是 Coding；
- AI 还可能增加验证、返工和架构治理成本；
- 吞吐会受跨部门依赖、排队和并行在制品影响。

因此，15%与团队负责人估计的 20%–30%都只能作为**情景参数**。最终应以真实 Case 的
Human Touch Time、Lead Time、质量和返工分桶数据校准。

## 领导汇报可用话术

推荐：

> 高质量外部研究给出的不是一个统一提效数字，而是一个清晰边界：简单、受控任务中，AI 曾实现
> 约 21%到 55.8%的任务级提速；但在熟悉的成熟代码库真实任务中，也观察到平均慢 19%。因此我们
> 不能用 Demo 推演生产交付，必须用自己的真实 Case、现有 AI 工作流基线和同一质量门槛测量。

> 两项 Microsoft 研究显示，其样本中的编码活动约占工作时间的低双位数，但它们不能替代我们的
> 团队测量。它们支持的只是：编码并非研发交付的全部，单纯更换生成模型不必然带来同等比例的
> 端到端人效提升。

不推荐：

- “行业数据证明开发人员只有 15% 时间写代码。”
- “AI Coding 最多只能提升整体 18%。”
- “DORA 证明 AI 会降低研发效率。”
- “Kimi K3 已经能显著提升可视化团队人效。”
- “AI 生成代码质量一定更差/更好。”
