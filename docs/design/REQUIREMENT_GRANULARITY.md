# 评测需求粒度规范

## 结论

主评测需求不应该“非常粗”，也不应该把实现和测试答案全部写死。

推荐使用：

> 内部完整需求真相 + 分阶段披露的真实业务上下文 + 独立隐藏验收。

主 Case 不再在 T0 把 2-4 页完整要求一次性投喂给 Agent。完整文档用于固定
评测真相，实际运行按 `ITERATIVE_REQUIREMENT_LOOP.md` 的阶段逐步披露。

## 1. 为什么不能只给一句自然语言

过粗的需求会把结果混入大量偶然因素：

- 不同 Agent 对需求的猜测不同；
- 失败可能来自信息缺失，而不是开发能力；
- 难以判断模型是否做错；
- 多次运行不可比较。

这类题适合评估“需求澄清能力”，不适合作为全部基准。

## 2. 为什么不能把需求写成实现说明书

过细会把任务降级成照抄：

- 泄露架构答案；
- 泄露验收点；
- 无法测试方案判断；
- 与真实产品需求不符；
- 模型可以针对固定断言刷题。

## 3. 三层需求包

### A. 初始业务 Brief

模拟产品、运营或业务方在立项初期的真实表达，只包含：

- 为什么做；
- 谁使用；
- 当前已经确认的少量关键行为；
- 已知输入与参考材料；
- 业务方此时真正能说清的约束。

它可以存在合理歧义，通常控制在 0.3-1 页。Agent 需要主动区分事实、假设和待确认项。

### B. 阶段化上下文包

模型提问后，平台按预设剧本给出当前阶段可知的答案；POC 后再追加真实会在
评审中出现的视觉、交互和生产化反馈。记录：

- 是否主动识别关键歧义；
- 提问是否抓住高返工风险，而不是穷举低价值问题；
- 是否在没有答案时明确假设。
- 是否维护精简的 Requirement Ledger；
- 是否在后续轮次保持早期关键约束。

第一阶段可先由人工选择答案，后续再做 Stakeholder Simulator。

### C. 内部完整需求真相与验收契约

模型不可见，包含：

- 最终已知的完整业务要求；
- 构建和测试命令；
- 功能与交互断言；
- 视觉参考和容差；
- 性能阈值；
- 禁止行为；
- 业务语义规则；
- 评分权重和失败上限。

## 4. 推荐评测集比例

- 20% 明确工程任务：测纯执行与回归；
- 60% 中等粒度真实需求：作为主评测；
- 20% 模糊探索任务：测澄清与方案能力。

首批主 Case 采用“模糊起点、分阶段收敛”的复杂业务切片；“起点不完整”不等于
故意缺失答案，而是让答案在符合真实研发节奏的时间点出现。

## 5. 难度分级与任务类型体系

高质量困难 Case 的难度应来自真实工作，而不是永久隐藏必要信息。必要信息必须
能通过提问、数据样例、POC 反馈或后续上下文包获得。

### 任务类型分类（6 类）
- `feature-dev`：图表/业务组件开发
- `bug-hunting`：缺陷排查与竞态修复
- `perf-tuning`：大数据量与 Canvas/WebGL 内存调优
- `reconstruction`：高保真产品复刻与视觉还原
- `greenfield-3d`：从零 3D 前沿探索
- `refactor-migrate`：技术栈迁移与重构

### 难度分级阶梯（4 级）
- 🥉 **Bronze（青铜）**：确定性基础任务，单图表与静态映射，通过率目标 > 90%；
- 🥈 **Silver（白银）**：业务组件级任务，复合图表、层级树、自适应 Resize、时序竞态；
- 🥇 **Gold（黄金）**：生产级复杂系统，时序叙事动画、万级数据点 Canvas 自绘、内存无泄漏；
- 💎 **Diamond（钻石）**：架构级攻坚与前沿 3D，WebGL/Shader 空间计算、相机拾取交互。

详细定义见 [任务分类分级与本地轻量隔离规范](TASK_TAXONOMY_AND_LOCAL_ISOLATION.md)。

## 6. Case 使用 P0/P1/P2 分层


- P0：形成真实可用的业务闭环。P0 未达标，整体不能判为“可替代人工交付”；
- P1：真实项目中常导致返工的复杂交互和业务边界；
- P2：生产化所需的性能、稳定性、兼容和可维护性。

分层不是给模型降低要求，而是让不同模型的完成上限可测，避免结果只有“通过/失败”。

## 7. 首批 Case 的信息控制

| 信息 | 模型可见 | 验收器可见 |
|---|---:|---:|
| 业务目标 | 是 | 是 |
| 用户与使用场景 | 是 | 是 |
| 输入数据 | 是 | 是 |
| 关键交互 | 是 | 是 |
| 推荐技术方案 | 通常否 | 可记录 |
| 具体文件和函数 | 否 | 是 |
| 隐藏边界样本 | 否 | 是 |
| 精确视觉容差 | 否 | 是 |
| 性能阈值 | 可给区间 | 是 |
| 评分权重 | 否 | 是 |

## 8. 防止需求不真实

正式 Case 需要记录来源类型：

- `observed`: 从现有产品或代码行为提取；
- `historical`: 从提交、缺陷或历史需求提取；
- `proposed`: 基于真实系统提出的新需求；
- `synthetic`: 纯合成题。

报告中不得把 `proposed` 写成“业务已经提出”。

## 9. 瓶颈型 Case 准入门槛

正式进入领导报告前，每个主 Case 需要满足：

- 有真实产品、提交、缺陷或历史需求证据；
- 原人工成本不能只是一个很快完成的小需求；
- 至少有一个过去明显耗时的环节：需求理解、方案、视觉返工、复杂交互、性能、联调或回归；
- 能定义“业务可接受”的质量门槛；
- 能记录 Agent 运行时间以及人工澄清、Review、修复和验收时间；
- 至少运行两个模型或版本，确认结果有区分度。

若多个模型的 P0 pass@1 都接近满分，且人工接管时间几乎为零，该 Case 降级为 smoke/calibration，不继续作为核心提效证据。
