# 迭代式需求收敛评测协议

## 核心决策

主评测单位不是“一份 Prompt 生成一份代码”，而是一次完整的：

> 模糊业务意图 → 澄清 → POC → 反馈 → 修改 → 业务验收

完整需求文档仍然保留，但它是评测方掌握的 `requirement truth`，不能在
T0 一次性全部交给 Agent。Agent 只会按阶段获得当时真实可知的信息。

## 为什么这样测

可视化研发的主要成本经常位于编码之外：

- 业务方和开发共同把模糊想法变成可实现方案；
- 用 POC 帮助所有人发现自己一开始没有说清的需求；
- 通过截图、走查和试用发现视觉与交互偏差；
- 在小改动中反复引入和修复回归；
- 长上下文中关键约束被稀释或遗忘。

因此，单次投喂完整 Spec 只能测长上下文执行能力，不能回答模型能否减少
真实开发中的人类注意力消耗。

## 标准阶段

| 阶段 | Agent 获得的信息 | 必须产出 | 主要观察 |
|---|---|---|---|
| S0 模糊 Brief | 业务目标、用户、最小背景 | 需求理解、关键问题、首轮方案 | 问题质量、是否抓住业务风险 |
| S1 需求对齐 | 固定答复、数据样例、边界卡片 | Requirement Ledger、POC 计划 | 收敛速度、假设透明度 |
| S2 首个 POC | 对首版的固定评审反馈 | 可运行 POC、差距清单 | 首版可用度、视觉判断 |
| S3 业务细化 | 交互、视觉、状态反馈包 | 修改版与回归证据 | 约束保持、微调成本 |
| S4 生产化 | 性能、响应式、异常和集成要求 | 候选交付物 | 工程完整性、回归情况 |
| S5 验收 | 自动检查与人工走查问题 | 修复或明确剩余边界 | 达标轮数、人工接管量 |

不是每个 Case 都必须使用全部阶段，但阶段顺序和可见信息必须固定，才能比较模型。

## Requirement Ledger

每轮后 Agent 必须更新一个短小、机器可读的需求账本：

```yaml
must:
  - id: R-001
    statement: 章节切换后未被本章替换的节点位置保持稳定
    source_stage: S1
    status: implemented
    evidence: src/example.ts:42
should: []
may: []
decisions: []
open_questions: []
assumptions: []
```

账本用于缓解注意力稀释，但不能代替代码、测试和页面证据。评测器检查：

- 关键约束是否进入 `must`；
- 后续轮次是否遗忘或错误改写；
- 代码状态与账本声明是否一致；
- Agent 是否能主动压缩上下文，而不是无限追加文档。

## 固定剧本与真实人工

为了兼顾真实性和可比性，采用双轨：

1. **标准回归模式**：使用固定的 stakeholder response / review packet，所有模型收到相同信息；
2. **探索模式**：由真实产品、设计或开发人员回答，但所有人工输入、耗时和新增要求必须记入事件日志。

领导报告的模型横向比较以标准回归模式为主；探索模式用于发现新 Case 和理解失败原因。

## 上下文注意力测试

不靠无意义地塞长文制造难度，而是在真实阶段中记录：

- 每轮可见上下文字节数和文件数；
- 新增 `must` 约束数；
- 已知约束在后续版本的保持率；
- 关键约束遗漏、冲突和回归；
- Agent 主动摘要、建立账本和验证的行为；
- 为修正上下文误解所需的人工分钟数。

可以在 S1、S2、S3 分别引入必要约束，观察“最近信息偏置”和早期约束遗忘。

## 终止与成功

运行在以下情况结束：

- 达到业务可接受门槛；
- 用完最大迭代轮数；
- 超过人工、自然时间或费用预算；
- 出现无法恢复的构建、隔离或运行错误；
- Reviewer 判定继续修改的成本已不低于当前团队基线。

成功不是“代码写完”，而是以受控的人类投入达到可验收状态。

## 主基线

第一优先基线是团队当前的 AI 协作流程：

> 工程师 + Codex + 当前主力 GPT 模型

Kimi K3 等候选必须与这个基线比较。纯人工历史数据可作为背景，但不能把
“比纯手写快”误报成“值得切换模型或工作方式”。
