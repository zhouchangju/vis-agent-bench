# Vis Agent Bench 产品需求

## 1. 要解决的问题

可视化团队会持续遇到新模型、新版本、新 CLI 和新客户端。一次性测评无法回答：

- 新版本是否值得切换；
- 哪一类可视化任务适合哪种 Agent；
- 模型能力提升是否减少了真实人工投入；
- 候选模型是否比团队现有 Codex + 主力 GPT 工作流更快收敛；
- 模糊需求、长上下文和多轮微调是否仍是主要瓶颈；
- 漂亮 Demo 能否通过工程、视觉、交互和业务验收；
- 历史版本是否发生能力回退。

## 2. 产品目标

建立一套长期运行的评测与回归平台：

1. 使用真实或经过脱敏的可视化研发任务；
2. 支持 API、CLI、客户端和半自动 Runner；
3. 在隔离工作区中执行任务；
4. 自动收集日志、代码差异、截图、视频、时间和可获得的 Token/费用；
5. 执行构建、测试、浏览器、视觉、性能和业务验收；
6. 生成可回溯的模型对比与领导报告。
7. 支持模糊 Brief、澄清、POC、反馈、修改和验收的多阶段会话。

## 3. 非目标

第一阶段不追求：

- 建立通用大模型排行榜；
- 用一个总分替代任务适用性判断；
- 100% 取消人工视觉和业务抽检；
- 一开始就支持所有客户端；
- 在候选尚未验证时批量建设几十个 Case。

## 4. 第一阶段成功标准

- 形成 3 个来自真实瓶颈的高质量正式 Case；
- 至少跑通一种 CLI/API Runner；
- 至少跑通一种半自动客户端 Runner；
- 每次运行保留可复现证据；
- 自动生成一份包含质量、人效和边界的 HTML/Markdown 报告；
- 能回答“需求收敛、编码、测试微调分别省了多少，是否优于当前工作流”，而不是只回答模型能否生成 Demo。

主 Case 必须先达到业务质量门槛，再计算人效。简单 smoke 结果不得作为“大幅提效”的核心证据。

## 6. 核心评测假设

首轮不预设 Kimi K3 会在编码上显著领先。重点验证：

1. 它是否能提出更少但更关键的澄清问题；
2. 它是否能用较低人工成本形成可评审 POC；
3. 它的前端视觉首版质量是否减少微调轮数；
4. 当上下文逐步增加时，是否能保持关键约束；
5. 最终是否降低从模糊需求到可验收交付的 Human Touch Time。

如果只在方案分析或视觉首版上更好，也应报告为局部优势，而不是“研发模式发生本质改变”。

## 5. 核心用户

- 可视化团队负责人：决定模型和工作方式是否值得推广；
- 可视化工程师：了解不同 Agent 的适用任务；
- 质量 Reviewer：复核自动验收和失败样本；
- 平台维护者：增加 Runner、Case 和 Evaluator。
